# שלב 2 — סכמת מסד הנתונים

## הרצה ובדיקה עצמית

מתיקיית הפרויקט הראשית, כאשר Docker Desktop פועל:

```powershell
docker compose up -d --wait
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/apply-schema.ps1
```

הפקודה השנייה יוצרת את הטבלאות ב-`VotesDb` הקיים. אפשר להריץ אותה שוב בלי למחוק
רשומות או לאפס את מועדי הבחירות. אין צורך למחוק את ה-volume של שלב 1.
זהו צעד הקמה מפורש; עליית ה-API לבדה עדיין אינה יוצרת את הטבלאות.

להצגת הטבלאות והמצב הראשוני:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/invoke-sql.ps1 -Query "SHOW TABLES; SELECT * FROM ElectionSettings; SELECT COUNT(*) AS PeopleCount FROM People;"
```

צריכות להופיע `Kalpi`, `People` ו-`ElectionSettings`. לאחר שלב 2 ולפני שלב 3 טבלאות הבוחרים
והקלפיות ריקות. ב-`ElectionSettings` יש שורה אחת, `Id=1`, והמועדים הם `NULL`.
משמעותם: טרם נקבעו מועדי בחירות. עדיין אין מסך להגדרת המועדים.

להרצת בדיקות הסכמה:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/schema/test-schema.ps1
```

הבדיקות יוצרות מסד נפרד בעל שם אקראי שמתחיל ב-`KalpiTechTest_`, ומוחקות רק
את המסד שיצרו בסיום. הן משתמשות בחשבון root בתוך הקונטיינר לשם יצירה ומחיקה
של מסד הבדיקות. היישום ופקודת הקמת הסכמה משתמשים בחשבון `kalpitech`.
הסיסמאות אינן מועברות בשורת הפקודה ואינן מודפסות.

הבדיקות מאתחלות את קונטיינר MySQL של הפרויקט כדי לבדוק שימור נתונים. בזמן
האתחול החיבור למסד אינו זמין לזמן קצר. אין להפעיל את הבדיקה באמצע עבודה עם המסד.
הצלחת הבדיקה מסומנת ב-`All 22 schema checks passed.`

נקודות הבדיקה משלב 1 ממשיכות לפעול כרגיל. אם ה-API אינו פועל, הרץ
`.\scripts\run-api.ps1` ופתח `http://127.0.0.1:5080/health/db`.

## אחריות הקבצים

- `src/KalpiTech.Api/Data/Sql/001_initial_schema.sql`: הגדרת הטבלאות והאילוצים.
- `scripts/apply-schema.ps1`: מפעיל את סקריפט הסכמה על המסד הפעיל.
- `scripts/invoke-sql.ps1`: מעביר קובץ SQL או שאילתה ללקוח MySQL בתוך הקונטיינר.
- `tests/schema/test-schema.ps1`: בדיקות מול MySQL אמיתי, ללא כתיבה לנתוני היישום.
- קובצי SQL בתיקיית הבדיקות: נתוני דוגמה סינתטיים ובדיקת שימור עברית.

## הטבלאות והקשרים

`Kalpi` שומרת קלפיות. `KalpiId` הוא מפתח ראשי, ולכן לא יכולות להיות שתי קלפיות
עם אותו מזהה. `KalpiType` מקבל רק `Regular` או `Accessible`, כולל התאמת אותיות.

`PasswordHash` יכול להיות `NULL` עד שהמנהל יקבע סיסמה. זו החלטת ייצוג עבור
קלפי שטרם קיבלה סיסמה; בשלב ההתחברות קלפי כזאת לא תוכל להתחבר. השדה מיועד
לגיבוב בלבד, ולא לסיסמה גלויה. עדיין לא הוגדר חשבון מנהל או סיסמת מנהל.

`People` שומרת בוחרים. `Id` הוא `VARCHAR(9)` עם בדיקת תשע ספרות; אפסים מובילים
נשמרים. שני מפתחות זרים מפנים ל-`Kalpi`:

- `KalpiId`: שיוך הבוחר לקלפי.
- `VotedIn`: הקלפי שבה הצביע בפועל; מותר שתהיה שונה מהשיוך.

מפתח זר מונע הפניה לקלפי שאינה קיימת. `RESTRICT` מונע מחיקה או שינוי מזהה של
קלפי שרשומת בוחר מפנה אליה, כדי שלא יאבדו קשרים. החלפת נתונים בהמשך תצטרך
לטפל בבוחרים ובקלפיות בסדר מתאים ובטרנזקציה אחת.

ברירות המחדל הן `Voted=FALSE` ו-`NULL` עבור המייל, זמן ההצבעה ומקום ההצבעה.
אילוץ `CHECK` מאפשר רק שני מצבים עקביים: ללא הצבעה וללא זמן/מקום, או הצבעה
עם זמן ומקום. הוא אינו מחליף את העדכון המותנה והאטומי שנממש בשלב אישור ההצבעה.

הטבלאות משתמשות ב-InnoDB כדי לתמוך בטרנזקציות ובמפתחות זרים, וב-`utf8mb4`
כדי לשמור עברית. אורך השדות שלא הוגדרו במפורש ב-README הוא בחירת מימוש:
100 לשמות ולעיר, 255 למקום ולכתובת, 254 למייל ו-512 לגיבוב הסיסמה.
נתוני CSV ייבדקו מול אורכים אלה בשלב הטעינה.

## מועדי הבחירות

`ElectionSettings` מכילה שורה אחת בלבד עם `Id=1`:

| שדה | משמעות |
| --- | --- |
| `StartsAt` | תחילת הבחירות ב-UTC |
| `EndsAt` | סיום פעילות הקלפיות ב-UTC; חייב להיות אחרי ההתחלה |
| `LoadLockedUntil` | תחילת הבחירות ועוד 36 שעות |

`LoadLockedUntil` הוא עמודה מחושבת מסוג `STORED`: MySQL מחשב אותה ושומר את
התוצאה כאשר `StartsAt` משתנה. כך אין צורך להזין מועד שלישי שעלול להיות שגוי.
אותו מועד יסמן גם את סיום חלון הזנת המעטפות הכפולות.

לא נשמרת מחרוזת מצב שצריכה להתעדכן עם חלוף הזמן. בשלב הפעלת הבחירות השרת
יגזור הכנה, פעילות או סיום מתוך המועדים השמורים והשעה הנוכחית. המועדים עצמם
מתמידים במסד. השדות משתמשים ב-`DATETIME(6)`; הם אינם ממירים אזור זמן מעצמם.
האחריות לכתיבה ב-UTC ולהצגה בשעון ישראל תהיה בקוד השרת והממשק.

## מגבלות השלב

הקמה חוזרת באמצעות `IF NOT EXISTS` אינה משדרגת טבלה שכבר קיימת במבנה אחר.
בשינוי סכמה עתידי נוסיף סקריפט ממוספר חדש. MySQL מבצע Commit אוטומטי לפקודות
DDL; הקמת כל הטבלאות אינה טרנזקציה אחת. אם ההקמה נקטעת, מריצים שוב ומשלימים
טבלאות חסרות. טרנזקציית החלפת הנתונים העתידית תכלול פעולות נתונים, בלי DDL.

עדיין לא מומשו טעינת CSV, חשבונות, הרשאות, מסכי משתמש, הפעלת בחירות או אישור
הצבעה. הבדיקות בשלב זה מוודאות את אילוצי המסד ואת שימור הנתונים בלבד.
