# שלב 4 — התחברות וניהול סיסמאות

## הרצה

עצור את השרת הקודם במסוף שלו באמצעות Ctrl+C. בתיקיית הפרויקט הראשית:

```powershell
docker compose up -d --wait
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/apply-schema.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run-api.ps1
```

פתח `http://127.0.0.1:5080/` בדפדפן. ההתחברות כוללת את שני השדות מה-README:
מספר קלפי / מייל ועדת הבחירות, וסיסמה.

שם ההתחברות הזמני למנהל הוא `admin@kalpitech.local`, עד שהמשתמש יספק מייל.
הסיסמה הראשונית נמסרת בצ'אט ונמצאת מקומית ב-`.env` תחת `ADMIN_INITIAL_PASSWORD`.
היא אינה נשמרת בקוד, בתיעוד או ב-Git. זו סיסמת חשבון המנהל, בנפרד מסיסמאות MySQL.

בהקמה חדשה יש להגדיר `ADMIN_EMAIL` ו-`ADMIN_INITIAL_PASSWORD` ב-`.env` לפני
הפעלת השרת. הסיסמה הראשונית צריכה להכיל 12 עד 128 תווים, ואינה יכולה להיות
ערך הדוגמה. השרת יוצר את החשבון רק אם טבלת `AdminAccount` ריקה. אם החשבון
כבר קיים, ההפעלה משמרת את המייל ואת הסיסמה שבמסד. שינוי הערכים ב-`.env`
אינו משנה או מאפס חשבון שכבר נוצר.

## בדיקה עצמית

1. נסה להתחבר עם סיסמה שגויה. תוצג הודעת התחברות שנכשלה.
2. התחבר כמנהל. יוצג מסך ועדת הבחירות עם שתי פעולות ניהול סיסמאות.
3. קבע סיסמה לקלפי קיימת, למשל 2824 (רגילה) או 1409 (נגישה). השתמש בסיסמה
   באורך 12 עד 128 תווים. אין צורך להזין שוב את סיסמת המנהל לפעולה הזאת.
4. לחץ יציאה ובחר ביטול בחלונית: המסך אמור להישאר פתוח. בחר יציאה ואישור:
   המערכת תחזור למסך ההתחברות.
5. התחבר באמצעות מספר הקלפי והסיסמה שקבעת. יוצג סוג הקלפי המתאים; כלי ניהול
   סיסמאות אינם מוצגים ואינם מורשים גם בפנייה ישירה ל-API.
6. התחבר שוב כמנהל ונסה להחליף את סיסמתו עם סיסמה נוכחית שגויה. הפעולה תידחה.
7. החלף עם הסיסמה הנוכחית התקינה. תוחזר למסך ההתחברות. הסיסמה הישנה לא תעבוד;
   החדשה תעבוד. התחברויות ישנות של המנהל, גם בדפדפן אחר, יידחו בבקשה הבאה.
8. עצור והפעל את השרת מחדש. הסיסמה החדשה צריכה להמשיך לעבוד ולא לחזור לסיסמה
   הראשונית מתוך `.env`.

מספר קלפי שטרם נקבעה לו סיסמה אינו יכול להתחבר. ניתן גם לשנות סיסמת קלפי
קיימת; ההתחברויות הקודמות של הקלפי יידחו בבקשה הבאה.

## המושגים החדשים

**Authentication — אימות זהות:** השרת בודק מי מתחבר. הוא מחפש את החשבון
במסד ומשווה את הסיסמה שהוזנה לגיבוב שמור באמצעות `PasswordHasher` המובנה.
הגיבוב משתמש ב-PBKDF2 וב-salt, כך שגם שתי סיסמאות זהות אינן חייבות ליצור אותו
גיבוב. לא שומרים סיסמה גלויה במסד ולא מממשים אלגוריתם הצפנה משלנו.

**Cookie:** לאחר הצלחה השרת יוצר כרטיס התחברות מוגן ומחזיר אותו לדפדפן.
הדפדפן שולח אותו בבקשות הבאות. הוא מכיל זהות ותפקיד שקבע השרת — לא את
הסיסמה. `HttpOnly` מונע מקריאה רגילה ב-JavaScript לגשת ל-Cookie ההתחברות.
הוא אינו נשמר ב-localStorage. ההתחברות מוגבלת לשמונה שעות, ללא הארכה אוטומטית.

**Claims:** פרטי הזהות שבתוך כרטיס ההתחברות: מזהה חשבון, תפקיד ומספר קלפי
כאשר זה חשבון קלפי. סוג הקלפי ומספרה מגיעים מהמסד. הם אינם מתקבלים מהדפדפן
כפרטי הרשאה.

**Authorization — הרשאה:** לאחר שמזהים את החשבון, בודקים מה מותר לו לעשות.
`[Authorize]` דורש התחברות ו-`[Authorize(Roles = "Admin")]` דורש מנהל.
בשלב הזה נלמדת ההרשאה הבסיסית הדרושה לניהול סיסמאות; חיפוש והצבעות עדיין לא קיימים.
הסתרת כפתור בדפדפן מסייעת לממשק, אך האכיפה עצמה מתבצעת בשרת.

**CSRF:** מכיוון שדפדפן שולח Cookies בעצמו, פעולות שינוי דורשות גם אסימון
שהעמוד קיבל מהשרת. JavaScript שולח אותו בכותרת `X-CSRF-TOKEN`. השרת בודק
אותו גם בהתחברות וגם ביציאה ובשינוי סיסמאות. לאחר שינוי זהות מבקשים אסימון
חדש, כי האסימון קשור לזהות הנוכחית. בנוסף Cookies מוגדרים עם SameSite=Strict.

## אחריות הקבצים

| רכיב | אחריות |
| --- | --- |
| `Controllers/AuthController.cs` | נתיבי התחברות, זהות מחוברת, יציאה וניהול סיסמאות |
| `Contracts/AuthRequests.cs` | מבנה הבקשות ואימות שדות חובה ואורכים |
| `Models/LoginAccount.cs` | ייצוג פנימי של חשבון; הגיבוב אינו מוחזר ללקוח |
| `Data/AccountStore.cs` | שאילתות פרמטריות, יצירת מנהל ושמירת גיבובים |
| `Data/DatabaseConnectionFactory.cs` | הגדרות חיבור משותפות, במקום לשכפל אותן בכל רכיב |
| `Services/AccountCookies.cs` | יצירת Claims, בדיקת חשבון בכל בקשה וביטול התחברות אחרי שינוי סיסמה |
| `Data/Sql/002_admin_account.sql` | טבלת מנהל יחיד: Id, EmailAddress ו-PasswordHash |
| `wwwroot/index.html` | מבנה המסכים, שדות וכפתורים ב-HTML עם כיוון עברי |
| `wwwroot/css/site.css` | עיצוב בסיסי והתאמה למסך קטן |
| `wwwroot/js/app.js` | fetch ל-API, טיפול בתגובות ומעבר בין המסכים |

`Program.cs` מרכיב את הרכיבים ואת סדר הטיפול בבקשה: קבצים סטטיים, אימות זהות,
בדיקת הרשאה ולבסוף פעולה ב-Controller. `AddControllersWithViews` מספק את שירותי
מסנן CSRF המובנה; המסכים עצמם נשארים קובצי HTML, ללא Razor או Framework של פרונט.

## ביטול התחברויות ושמירה לאחר אתחול

השרת בודק בכל בקשה שהחשבון עדיין קיים, שסוגו לא השתנה ושגיבוב הסיסמה תואם
לגרסה שהייתה בעת ההתחברות. בתוך ה-Cookie המוגן נשמרת טביעת גיבוב בלבד, לא
גיבוב הסיסמה עצמו. שינוי סיסמה משנה את הטביעה ומבטל את הכרטיסים הישנים.
שינוי סיסמת מנהל שומר רק אם הגיבוב הנוכחי עדיין תואם למה שאומת, כדי לזהות
שינוי מקביל ולא לדרוס אותו בשקט.

מפתחות Data Protection נשמרים מקומית בתיקיית `.local/keys`, המוחרגת מ-Git.
ב-Windows הם מוגנים ב-DPAPI של משתמש מערכת ההפעלה. אותה זהות Windows ואותה
תיקיית מפתחות מאפשרות לכרטיס תקין להישאר קריא לאחר אתחול השרת.

יציאה מוחקת את Cookie ההתחברות בדפדפן. זה אינו מנגנון ניהול Sessions במסד,
ולכן עותק של Cookie שהועתק מראש אינו מתבטל מעצם היציאה בלבד. שינוי סיסמה
כן מבטל אותו בבקשה הבאה. ניהול Sessions נוסף, אם יידרש, הוא הרחבה עתידית.

הרצה מקומית נעשית ב-HTTP על 127.0.0.1. Cookie מקבל Secure כאשר הבקשה היא HTTPS;
לפני פריסה מחוץ למחשב יש להגדיר HTTPS ו-Secure תמיד. עדיין לא נוספה הגבלה על
קצב ניסיונות התחברות. השלב נועד להרצה וללמידה מקומית.

## בדיקות אוטומטיות

כדי לבנות בלי להתנגש בקובצי שרת אחר שפועל מהפרויקט:

```powershell
dotnet build src/KalpiTech.Api --no-restore -p:UseAppHost=false -o .local/stage04-build
.\.venv\Scripts\python.exe -m unittest discover -s tests/auth -p test_auth.py -v
```

הבדיקות מפעילות שרת ומסד MySQL זמניים נפרדים, משתמשות בנתונים וסיסמאות
סינתטיים ומנקות אותם בסיום. אין שינוי בסיסמאות הקלפיות במאגר הפעיל.

כל 12 בדיקות ההתחברות עברו. נבדקים התחברות מנהל וקלפי רגילה ונגישה, סיסמה שגויה, קלפי ללא סיסמה,
401 ללא התחברות, 403 כאשר קלפי מנסה לבצע פעולת מנהל, CSRF, HttpOnly,
Cookie מזויף, שינוי סיסמה והתחברויות ישנות, יציאה ושימור סיסמה ו-Cookie
לאחר אתחול שרת הבדיקה. בניית הגרסה החדשה הסתיימה ללא אזהרות או שגיאות.

מסך התחברות המנהל ויציאה נבדקו גם דרך דפדפן. ביטול חלונית היציאה, מסך צר
ומילוי טפסי שינוי הסיסמה דרך הדפדפן עדיין דורשים בדיקה ידנית; פעולות הסיסמאות
עצמן נבדקות מול ה-API. חיפוש בוחרים, הרשאות הצבעה ופעולות הוועדה הנוספות
טרם מומשו בשלב זה.
