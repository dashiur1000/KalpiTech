# שלב 14 — יומן פעולות

## מטרת השלב

`AuditLogs` הוא יומן היסטורי נפרד מנתוני הבוחרים. `People` מתאר את מצב ההצבעה הנוכחי; היומן מתאר מי ניסה לבצע פעולה, מתי ומה הייתה התוצאה. היישום מאפשר הוספה וקריאה בלבד ואינו חושף API לעדכון או למחיקה.

## עדכון הסכמה

בהרצה מקומית יש להחיל את migration החדש בלי למחוק נתונים:

```powershell
./scripts/apply-schema.ps1
```

בהרצת Docker הסקריפטים בתיקיית `Data/Sql` מופעלים לפי הסדר בכל עלייה, ולכן `004_audit_logs.sql` יוצר את הטבלה החסרה ומשמר מאגר קיים:

```powershell
docker compose -f compose.yaml -f compose.app.yaml up -d --build --wait
```

מבנה הטבלה:

| שדה | סוג | תפקיד |
| --- | --- | --- |
| Id | BIGINT AUTO_INCREMENT | מזהה הרשומה |
| OccurredAtUtc | DATETIME(6) | זמן UTC |
| ActorRole | VARCHAR(32) | הרשאת המבצע |
| ActorIdentifier | VARCHAR(254) | מזהה המבצע |
| Action | VARCHAR(64) | סוג הפעולה |
| TargetType | VARCHAR(32) | סוג היעד |
| TargetIdentifier | VARCHAR(128) | מזהה יעד אופציונלי |
| Result | VARCHAR(32) | Success, Blocked, Failed או Skipped |
| Details | VARCHAR(1000) | תיאור כללי ובטוח |
| CorrelationId | CHAR(36) | קישור בין אירועים מאותה בקשה |

נוספו אינדקסים על זמן האירוע, הפעולה, מזהה המבצע והתוצאה.

## אטומיות ההצבעה

`VoteStore` נועל את הגדרות הבחירות ואת רשומת הבוחר, מבצע את כל הבדיקות, מעדכן את `People`, מוסיף רשומת הצלחה דרך `AuditLogStore`, ורק אז מבצע `Commit`. כשל בעדכון, בכתיבת היומן או ב־Commit גורם ל־Rollback, ולכן אין הצבעה ללא Audit הצלחה ואין Audit הצלחה ללא הצבעה. ניסיונות חסומים נרשמים בהתאם לתוצאה שנצפתה תחת הנעילות. במקרה של כשל במסד מתבצע ניסיון נפרד ובטוח לרשום כשל; אם המסד כולו אינו זמין, אין אפשרות להבטיח שרשומת הכשל תישמר.

שליחת המייל נשארת אחרי ה־Commit ואינה מבטלת הצבעה. נרשמת עבורה תוצאה נפרדת: נשלח, דולג או נכשל.

## API והרשאות

`GET /api/audit` זמין ל־`Admin` בלבד ותומך בפרמטרים `page`, `pageSize`, `action`, `result`, `actorIdentifier`, `from`, `to`. ברירת המחדל היא 25 רשומות, המקסימום 100, והמיון מהחדש לישן. התשובה כוללת `items`, `page`, `pageSize`, `totalCount`, `totalPages`.

מספר זהות נשמר במסד לצורכי תחקור מורשה אך מוחזר כמספר מוסתר, לדוגמה `*****4567`. היומן אינו שומר או מחזיר סיסמאות, גיבובים, Cookies, טוקנים, מפתחות API, תוכן מייל או טקסטי חריגה.

## בדיקה ידנית

1. התחבר כמנהל ופתח „יומן פעולות”.
2. ודא שמוצגת רשומת צפייה ביומן ושהזמן מוצג לפי שעון ישראל.
3. התחבר לקלפי, חפש בוחר ואשר הצבעה; התחבר שוב כמנהל ובדוק את רשומות החיפוש, האישור והמייל.
4. נסה להצביע שוב ובדוק שמופיעה תוצאה „נחסם”.
5. בדוק סינון לפי פעולה, תוצאה, מספר קלפי ותאריכים ועבור בין עמודים.
6. ודא שיעד מסוג בוחר מוצג עם ארבע ספרות אחרונות בלבד.

בדיקות האינטגרציה נמצאות ב־`tests/audit/test_audit.py`. הן משתמשות במסד זמני, בפרטי משתמש סינתטיים ובמדמה מייל מקומי בלבד.

לאחר תיקון קריאת `CorrelationId` והרצת המערכת בקונטיינרים עברו 91 בדיקות אינטגרציה, כולל כל בדיקות השלבים הקודמים. בנוסף עברו בניית ‎.NET 8 ללא אזהרות, בדיקת תחביר JavaScript, אימות קישורי רכיבי הממשק ובניית Docker. בדיקת קבלה מאומתת מול `GET /api/audit` החזירה עימוד תקין ולא חשפה מספר זהות מלא.

## מגבלה ידועה

היומן נמצא באותו מסד כמו נתוני הבחירות. כאשר MySQL אינו זמין כלל, גם רישום כשל חדש אינו אפשרי. מערכת ייצור רחבה יכולה בעתיד להוסיף יעד Audit חיצוני עמיד, אך הוא אינו נדרש להדגמת הפרויקט הנוכחית.
